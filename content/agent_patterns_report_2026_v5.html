에이전트 기본 활용 패턴

업무 성격에 따라 자주 쓰는 에이전트 패턴을 정리한다. 기본 화면에서는 구조·적용 기준·장단점만 보고, 구체적인 활용 사례와 구성 방법은 각 패턴에서 펼쳐서 확인할 수 있다.

요약기본 패턴업무별 조합활용 시 고려사항선택 기준참고자료

1. 패턴 요약

먼저 각 패턴이 실제로 어떻게 움직이는지만 비교한다. 장단점은 상세 항목에서 설명한다.

패턴동작 방식주로 쓰는 곳주의점
Agent Loop + Tool판단 → 실행 → 결과 확인을 해결될 때까지 반복버그 조사, 코드 수정, 장애 분석종료 조건과 검증 신호가 약하면 반복이 길어짐
Workflow + Agent정해진 순서 중 판단이 필요한 단계만 Agent가 처리CI, 회귀 테스트, 배포, 정기 처리탐색형 작업을 억지로 Workflow로 만들면 예외가 늘어남
Planner → Executor큰 일을 나누고 하나씩 실행하며 계획을 갱신장기 개발, 복잡한 성능 문제, 대형 기능작은 작업에는 오버헤드가 큼
Evaluator / Critic작업 결과를 다시 검토하고 문제면 수정PR review, 테스트 검토, 품질 자동화LLM 평가만으로 정답을 보장할 수 없음
Manager + Subagents독립 작업을 여러 Agent가 동시에 처리하고 결과 통합병렬 조사, 여러 가설 검증, 대규모 탐색의존성이 큰 작업은 병렬화 이득이 작음
Skills필요한 업무 지식과 절차를 불러와 사용사내 빌드법, 테스트법, 코드 규칙오래된 Skill은 잘못된 행동을 안정적으로 반복시킴
Tools / MCP실제 시스템을 직접 조회·실행하도록 기능 연결Git, CI, 빌드, 테스트, DB, 브라우저Tool 설계와 반환 데이터 품질이 Agent 성능에 직접 영향
A2A독립 Agent에게 작업을 맡기고 결과를 받음팀/서비스가 분리된 Agent 시스템한 시스템 내부에서는 대개 Tool 호출보다 복잡함

2. 기본 활용 패턴

각 패턴의 핵심만 먼저 보고, 실제로 어떤 상황에서 어떻게 구성하고 사용하는지는 「활용 예시」를 펼쳐서 확인한다.

01

Agent Loop + Tool

Agent가 직접 행동하고, 실행 결과를 보고, 다음 행동을 다시 결정하는 기본 구조.

Agent가 한 번 답하고 끝나는 것이 아니라, 직접 Tool을 실행하고 결과를 본 뒤 다음 행동을 다시 결정한다.요청 → Agent 판단 → Tool 실행 → 결과 확인 → 해결될 때까지 반복

적용 기준
처음부터 작업 순서를 정하기 어렵고, 실행 결과에 따라 다음 행동이 달라지는 경우. 예: 원인 미상의 crash, 테스트 실패, 성능 저하.
사용 방식
Agent에게 목표와 완료 조건을 주고, 조사·수정·검증에 필요한 Tool을 연결한다. 세부 순서는 Agent가 결정한다. 실패하면 같은 Tool을 다른 방식으로 쓰거나 새로운 가설을 세워 반복한다.
장점
  • 예외 대응: 예상하지 못한 로그나 코드 구조가 나와도 다음 행동을 바꿀 수 있다.
  • 절차 작성 감소: 사람이 모든 분기와 예외를 Workflow로 미리 구현할 필요가 없다.
  • 자기 검증: Build/Test 같은 Tool이 있으면 수정 후 결과를 직접 확인하고 다시 고칠 수 있다.
단점
  • 반복 비용: 방향을 잘못 잡으면 검색·수정·테스트 호출이 계속 늘어난다.
  • 종료 판단: '충분히 해결됨'을 판단할 기준이 없으면 너무 일찍 끝내거나 계속 탐색할 수 있다.
  • 긴 작업 관리: 작업이 길어지면 context 정리, 상태 저장, 재시도 구조가 필요하다.

참고: OpenAI — Harness engineering

활용 예시 펼치기

이 패턴은 처음부터 정답으로 가는 순서를 알 수 없는 문제에 쓴다. 사람이 세부 절차를 정해주는 대신 목표와 확인 기준을 주고, Agent가 결과를 보면서 다음 행동을 바꾼다.

예시 1. 매출 하락 원인 조사

상황지난달 특정 지역의 매출이 20% 떨어졌는데 이유를 모른다. 광고, 주문, 환불, 배송 등 어느 쪽이 문제인지도 모른다.

구성Agent가 매출 데이터, 주문·환불 기록, 광고 성과, 배송 이슈를 직접 조회할 수 있게 연결한다. 완료 기준은 “하락 원인을 근거와 함께 설명하고 대응 항목을 정리하는 것”으로 둔다.

매출 데이터 확인 → 지역/상품별로 원인 범위 축소 → 주문량은 정상, 환불률 증가 발견 → 환불 사유 확인 → 배송 지연 비율 증가 발견 → 배송 이슈 조회 → 특정 물류센터 장애 확인 → 원인과 영향 범위, 대응안 정리

사용Agent에게 “매출이 왜 떨어졌는지 조사하고 근거까지 정리해”라고 맡긴다. 첫 조회 결과에 따라 다음 조회가 달라지므로 사람이 조사 순서를 미리 만들 필요가 없다.

이 패턴이 맞는 이유: 첫 결과를 보기 전에는 다음에 무엇을 확인해야 할지 알 수 없기 때문이다.

예시 2. 원인 미상의 프로그램 오류 수정

상황특정 파일을 열 때 간헐적으로 crash가 나지만 재현 조건과 문제 코드 위치를 모른다.

구성Repository 검색, Git history, 로그, 빌드, 테스트 실행 기능을 Agent가 직접 사용할 수 있게 한다. 완료 기준은 “재현 성공 → 원인 확인 → 수정 → 관련 테스트 통과”다.

재현 시도 → 로그 분석 → 관련 코드 검색 → 원인 가설 생성 → 테스트로 가설 확인 → 코드 수정 → 빌드/테스트 → 실패 시 새 로그를 보고 다시 조사 → 통과할 때 종료

사용파일이나 함수 위치를 사람이 지정하지 않는다. Agent가 실제 실행 결과를 보면서 조사 범위를 좁히고, 수정 후 실패하면 다시 루프를 돈다.

이 패턴이 맞는 이유: 조사와 실행 결과가 다음 행동을 결정하는 전형적인 탐색형 문제이기 때문이다.

에이전트·툴 구성 펼치기

최소 구성은 판단하는 Agent + 상태를 볼 Tool + 행동할 Tool + 결과를 확인할 Tool이다.

Agent ├─ 관찰: 검색 / 로그 / 데이터 조회 ├─ 실행: 수정 / 명령 / API 호출 └─ 검증: 테스트 / 결과 조회 / 상태 확인 ↑ 결과를 다시 Agent가 읽고 반복
필수
문제 상태를 직접 확인할 수 있는 조회 기능, 실제 행동 기능, 성공 여부를 확인할 검증 기능
중요
Tool 결과를 짧고 구조적으로 반환해 Agent가 다음 행동을 판단하기 쉽게 만든다.
종료 기준
“문제가 해결됨”을 확인할 수 있는 테스트, 수치, 상태 등을 명확하게 둔다.
02

Workflow + Agent

실행 순서는 코드가 갖고, 판단이 필요한 일부 단계만 Agent가 처리하는 구조.

전체 순서는 기존 코드나 CI가 정하고, 사람이 판단하던 일부 단계만 Agent가 맡는다.정해진 단계 실행 → Agent 판단이 필요한 지점 → 결과에 따라 다음 단계 실행

적용 기준
실행 순서가 대부분 이미 정해져 있고 동일한 과정을 반복해야 하는 경우. 예: CI, 회귀 테스트, 배포, 매일 수행하는 분석.
사용 방식
코드로 표현 가능한 단계는 그대로 유지한다. 자연어 해석, 분류, 원인 추정처럼 규칙으로 만들기 어려운 지점에 Agent node를 삽입한다.
장점
  • 재현성: 어떤 단계가 언제 실행되는지 코드로 고정되어 운영과 디버깅이 쉽다.
  • 비용 통제: 모든 단계에서 모델을 호출하지 않고 필요한 곳에서만 사용한다.
  • 기존 시스템 활용: Jenkins, build script, test runner를 버리지 않고 Agent만 추가할 수 있다.
단점
  • 유연성 제한: 예상하지 못한 상황에서 Workflow 밖의 행동을 하기 어렵다.
  • 예외 폭증: 탐색형 문제를 Workflow로 만들면 if/branch가 계속 추가될 수 있다.
  • Agent 장점 감소: 사람이 하던 절차를 너무 세세하게 고정하면 Agent가 더 좋은 경로를 찾을 여지가 줄어든다.

활용 예시 펼치기

이 패턴은 업무 순서는 이미 정해져 있지만 중간에 사람 판단이 들어가는 반복 업무에 쓴다. 고정 단계는 기존 프로그램이 실행하고, 해석이 필요한 단계만 Agent에게 맡긴다.

예시 1. 매일 들어오는 비용 청구 처리

상황직원 비용 청구가 매일 들어온다. 영수증 저장, 금액 합계, 승인 결과 기록 순서는 항상 같지만 “회사 규정상 애매한 지출인지”는 사람이 판단하고 있다.

구성기존 비용 처리 Workflow는 유지하고, 규정 해석 단계에 Agent를 넣는다. Agent는 청구 내용과 회사 규정을 보고 “정상 / 추가 확인 / 규정 위반 가능성”으로 분류한다.

청구 접수 → 필수 항목 확인 → 금액 계산 → [Agent] 규정 해석/분류 → 정상: 자동 처리 → 애매함: 추가 자료 요청 → 결과 저장 및 보고

사용매번 Agent에게 전체 업무를 맡기는 것이 아니라, 규칙 코드로 만들기 어려운 한 지점만 Agent가 처리한다.

이 패턴이 맞는 이유: 대부분의 절차는 변하지 않고, 일부 판단만 자연어 이해가 필요하기 때문이다.

예시 2. CI 실패 자동 처리

상황빌드와 테스트는 자동화돼 있지만 실패하면 개발자가 로그를 읽고 환경 문제, flaky test, 실제 regression을 구분한다.

구성CI가 빌드·테스트를 실행하고 실패 로그를 Agent에게 전달한다. Agent는 원인을 분류하고 실제 regression이면 관련 변경을 조사해 수정 작업을 진행한다.

Build → Test → 실패 여부 확인 → [Agent] 로그 분석 및 실패 유형 분류 → 환경/flaky: 재실행 또는 기록 → regression: 관련 변경 조사 → 수정 → Test 재실행 → 결과 저장

사용빌드 순서나 테스트 실행 순서를 Agent에게 매번 판단시키지 않는다. 사람이 해석하던 실패 분석만 Agent로 대체한다.

이 패턴이 맞는 이유: 고정된 자동화 파이프라인에 판단 능력만 추가하면 되기 때문이다.

에이전트·툴 구성 펼치기

전체 흐름을 관리하는 Workflow와 일부 Agent 단계로 구성한다.

Workflow / Scheduler ├─ Step 1: 정해진 처리 ├─ Step 2: 정해진 처리 ├─ Agent Step: 해석 / 분류 / 판단 ├─ Step 4: 결과에 따른 실행 └─ 상태/결과 저장
Workflow
반복되는 순서, 재시도, 시간 조건, 데이터 전달을 관리한다.
Agent
규칙으로 만들기 어려운 분류, 해석, 원인 추정만 맡는다.
Tool
각 단계에서 실제 데이터를 읽거나 시스템을 실행한다.
03

Planner → Executor

길고 복잡한 작업을 먼저 작은 작업과 검증 항목으로 나눈 뒤 실행하는 구조.

큰 작업을 바로 수정하기 시작하지 않고, 먼저 할 일을 나눈 뒤 하나씩 실행하면서 계획을 계속 갱신한다.큰 요청 → 작업/가설 분해 → 실행 → 결과 반영 → 계획 갱신 → 완료

적용 기준
한두 번의 수정으로 끝나지 않고 여러 모듈·가설·검증 단계가 연결되는 경우. 예: 대형 기능 구현, 장시간 성능 개선, 복잡한 호환성 문제.
사용 방식
초기에 계획을 만들고 각 항목에 완료 조건을 둔다. 실행하면서 새 정보가 나오면 완료된 항목을 표시하고 계획을 추가·삭제·순서 변경한다. 계획은 고정 문서가 아니라 작업 상태다.
장점
  • 목표 유지: 긴 작업 중 눈앞의 오류에만 매달려 원래 목표를 잃는 문제를 줄인다.
  • 누락 방지: 구현, 테스트, 성능, 호환성처럼 여러 검증 항목을 추적하기 쉽다.
  • 중단·재개: 현재 어디까지 했는지가 남아 긴 실행을 이어가기 쉽다.
단점
  • 오버헤드: 작은 버그에도 계획을 만들면 바로 고치는 것보다 느리다.
  • 계획 고착: 초기 가설이 틀렸는데 계획을 계속 따르도록 만들면 탐색 능력이 떨어진다.
  • 상태 관리 필요: 오래된 계획과 실제 코드 상태가 어긋나지 않도록 갱신해야 한다.

활용 예시 펼치기

이 패턴은 한 번에 끝낼 수 없고 여러 단계가 연결된 큰 작업에 쓴다. Agent가 먼저 작업을 작은 단위로 나누고, 실행하면서 새 정보에 맞춰 계획을 계속 갱신한다.

예시 1. 신규 서비스 출시 준비

상황“신규 구독 서비스를 출시하자”처럼 목표만 있고 조사, 정책, 가격, 일정, 운영 준비 등 해야 할 일이 많다.

구성Agent가 해야 할 일을 조사/결정/실행 항목으로 나누고 각 항목에 결과물을 둔다. 시장 조사 결과가 나오면 가격 검토 순서를 바꾸는 식으로 계획을 수정할 수 있게 한다.

목표 입력 → 시장/경쟁사 조사 → 고객 요구 정리 → 가격·정책 초안 → 운영 요구사항 확인 → 리스크/누락 점검 → 실행 중 새 사실이 나오면 계획 수정 → 최종 출시 체크리스트 완성

사용처음 계획을 승인받고 멈추는 것이 핵심이 아니다. 계획을 “현재 작업 상태”로 유지하면서 Agent가 다음 할 일을 놓치지 않게 하는 것이 핵심이다.

이 패턴이 맞는 이유: 작업이 길어서 중간 문제에 매몰되기 쉽고, 여러 결과가 서로 다음 단계에 영향을 주기 때문이다.

예시 2. 성능 15% 개선

상황“계산 속도를 15% 개선”처럼 목표는 명확하지만 병목 위치와 해결 방법을 모른다.

구성Baseline 측정, profiler 분석, 가설별 실험, 기능 회귀 검사, 최종 benchmark를 작업 항목으로 만든다. 각 실험 결과에 따라 다음 가설의 우선순위를 바꾼다.

Baseline 측정 → 병목 후보 목록 작성 → 가설 A 실험 → 효과 없음, 제외 → 가설 B 실험 → 8% 개선 → 추가 병목 조사 → 가설 C 적용 → 17% 개선 → 회귀 테스트 → 최종 benchmark

사용Agent가 눈앞의 코드 하나만 최적화하지 않고, 목표 수치와 검증 항목을 끝까지 추적하게 한다.

이 패턴이 맞는 이유: 여러 가설을 순서대로 검증하고 긴 작업 상태를 관리해야 하기 때문이다.

에이전트·툴 구성 펼치기

별도 Planner Agent가 반드시 필요한 것은 아니다. 하나의 Agent가 계획 상태를 유지하면서 실행해도 된다.

Agent ├─ Plan: 할 일 / 가설 / 완료 기준 ├─ Execute: 조사 / 수정 / 실행 ├─ Check: 결과 확인 └─ Update Plan: 완료·추가·우선순위 변경
계획 상태
현재 할 일, 완료 항목, 새로 발견된 문제를 저장한다.
실행 Tool
계획 항목을 실제로 확인할 데이터·실행 기능이 필요하다.
갱신 규칙
새 사실이 나오면 초기 계획을 고집하지 않고 추가·삭제·순서 변경할 수 있어야 한다.
04

Evaluator / Critic

첫 결과를 최종 결과로 보지 않고 별도 평가 단계에서 검사한 뒤 수정시키는 구조.

구현이 끝났다고 바로 종료하지 않고, 결과를 다시 검토하는 단계를 하나 더 둔다. 문제가 있으면 수정 단계로 되돌린다.구현 → 테스트 → 별도 검토 → 문제 발견 → 수정 → 다시 검토

적용 기준
첫 결과의 품질 편차가 크거나, 자동으로 반복 검토할 가치가 있는 경우. 예: PR review, 테스트 누락 탐지, API 변경 검토, 문서/코드 품질 검사.
사용 방식
평가기준(rubric)을 구체적으로 준다. 가능하면 Build/Test/Static Analysis/Benchmark 같은 기계적 검증 결과도 함께 입력한다. Evaluator가 문제를 찾으면 수정 Agent가 고치고 다시 검사한다.
장점
  • 검토 자동화: 사람이 반복적으로 하던 '빠진 테스트가 있는가', '요구사항을 어겼는가' 같은 검토를 흡수한다.
  • 다른 시점의 context: 작성 과정의 논리에 끌려가지 않고 결과물만 다시 볼 수 있다.
  • 반복 개선: 한 번 생성하고 끝내는 것보다 품질을 끌어올릴 수 있다.
단점
  • 같이 틀릴 수 있음: 생성자와 평가자가 같은 잘못된 전제를 공유하면 두 번 확인해도 틀린다.
  • 비용 증가: 구현 후 다시 전체 context를 읽고 평가해야 한다.
  • 무한 수정: 평가기준이나 종료 조건이 모호하면 사소한 지적과 수정을 반복할 수 있다.

참고: Anthropic — Evals for AI agents

활용 예시 펼치기

이 패턴은 첫 결과를 바로 사용하기보다 한 번 더 품질 검사를 해야 하는 업무에 쓴다. 만드는 역할과 검사하는 역할을 분리하고, 기준을 통과하지 못하면 다시 수정한다.

예시 1. 고객 제안서 자동 작성

상황Agent가 고객 요구를 바탕으로 제안서를 만들 수 있지만 가격 누락, 요구사항 오해, 과장 표현 같은 실수가 생길 수 있다.

구성작성 Agent와 평가 단계를 나눈다. 평가 기준은 “필수 요구사항 포함, 숫자 일치, 금지 표현 없음, 근거 없는 약속 없음”처럼 명확하게 만든다.

고객 요구 입력 → 제안서 작성 → [Evaluator] 요구사항/숫자/정책 기준으로 검사 → 누락 발견 → 작성 결과 수정 → 다시 검사 → 기준 통과 시 최종본

사용평가기준을 “좋은 문서인지 봐줘”처럼 두지 않고, 체크할 항목을 구체적으로 정한다. 숫자나 필수 항목은 가능하면 프로그램으로도 검사한다.

이 패턴이 맞는 이유: 생성 능력과 오류를 찾는 능력을 분리하면 한 번 생성하고 끝내는 것보다 품질 편차를 줄일 수 있기 때문이다.

예시 2. 코드 변경 자동 리뷰

상황Agent가 기능을 구현하고 테스트까지 통과했지만, 경계 조건 누락이나 불필요하게 큰 수정이 남을 수 있다.

구성구현 결과와 diff, 요구사항, 테스트 결과를 별도 평가 단계에 넣는다. 평가 단계는 회귀 가능성, 테스트 누락, 성능·동시성 영향 등을 다시 본다.

구현 → Build/Test 통과 → [Evaluator] diff와 요구사항 재검토 → 경계 조건 누락 발견 → 테스트 추가 + 코드 수정 → Build/Test + 재검토 → 이상 없으면 완료

사용Evaluator가 구현 과정의 설명만 믿지 않고 최종 diff와 실제 검증 결과를 보도록 한다.

이 패턴이 맞는 이유: “테스트가 통과했다”와 “변경이 충분히 안전하다”는 같은 의미가 아니기 때문이다.

에이전트·툴 구성 펼치기

생성/실행 결과와 평가 단계를 분리하고, 평가 결과가 기준을 통과하지 못하면 다시 수정하게 한다.

작업 Agent → 결과물 ↓ Evaluator ├─ 평가 기준 ├─ 실제 검증 결과 └─ 원본 요구사항 ↓ PASS → 완료 / FAIL → 수정
평가기준
좋다/나쁘다가 아니라 확인할 항목을 구체적으로 정의한다.
독립 신호
숫자, 테스트, 정책 위반처럼 프로그램으로 확인 가능한 것은 Agent 평가와 함께 사용한다.
종료 조건
수정 횟수나 필수 통과 조건을 두어 사소한 지적이 무한 반복되지 않게 한다.
05

Manager + Subagents

한 Agent가 모든 내용을 처리하지 않고 독립 작업을 여러 실행 context로 나누는 구조.

큰 작업을 서로 독립적인 작은 작업으로 나눠 여러 Agent가 동시에 처리하고, 마지막에 결과를 합친다.큰 요청 → 독립 작업 분리 → 여러 Agent 병렬 실행 → 결과 통합

적용 기준
서로 기다릴 필요 없이 독립적으로 진행할 수 있는 작업이 여러 개 있거나, 한 context에 넣기에는 조사 범위가 너무 큰 경우.
사용 방식
먼저 병렬화 가능한 단위를 찾는다. 조사 작업은 비교적 쉽게 나눌 수 있다. 코드 수정은 같은 파일·상태를 공유하면 충돌하므로 별도 worktree나 명확한 모듈 경계를 둔다. 마지막 통합은 Manager가 담당한다.
장점
  • 시간 단축: Git history 조사와 profiler 분석처럼 독립 작업을 동시에 수행할 수 있다.
  • Context 확장: 각 Agent가 필요한 자료만 읽으므로 하나의 context에 모든 정보를 넣지 않아도 된다.
  • 가설 다양화: 서로 다른 가설이나 접근을 동시에 시험하기 좋다.
단점
  • 호출량 증가: 병렬성이 없으면 같은 문제를 여러 Agent가 중복해서 읽는 비용만 늘어난다.
  • 통합 비용: 결과가 충돌하거나 서로 다른 전제를 사용하면 Manager가 다시 정리해야 한다.
  • 공유 상태 충돌: 여러 Agent가 같은 코드/환경을 동시에 수정하면 conflict가 생긴다.

참고: Anthropic — Multi-agent research system · OpenAI — Symphony orchestration

활용 예시 펼치기

이 패턴은 서로 기다리지 않고 동시에 진행할 수 있는 일이 여러 개일 때 쓴다. 한 Agent가 모든 자료를 순서대로 보는 대신, 독립 작업을 여러 Agent에 나누고 마지막에 결과를 합친다.

예시 1. 해외 시장 진출 조사

상황한 국가 진출 여부를 판단하려면 시장 규모, 경쟁사, 규제, 고객 반응을 조사해야 한다. 네 조사는 대부분 서로 독립적이다.

구성Manager가 결과 형식을 정하고 네 개의 Subagent에 조사 범위를 나눈다. 각 Agent는 자기 주제만 깊게 조사하고, Manager는 결과를 비교해 하나의 결론으로 합친다.

Manager ├─ Agent A: 시장 규모 ├─ Agent B: 경쟁사 ├─ Agent C: 규제/법률 └─ Agent D: 고객 반응 ↓ 동시에 조사 각 결과 반환 → Manager가 공통 기준으로 비교 → 진출안 작성

사용같은 자료를 여러 Agent가 중복 조사하지 않도록 역할과 결과 형식을 명확하게 나눈다.

이 패턴이 맞는 이유: 작업이 독립적이어서 병렬로 수행하면 시간과 context를 줄일 수 있기 때문이다.

예시 2. 성능 Regression 원인 조사

상황최근 변경, profiler 결과, 테스트 패턴을 모두 봐야 하는데 한 Agent가 순서대로 조사하면 시간이 길고 context가 커진다.

구성Git 조사 Agent, profiler 분석 Agent, 테스트 분석 Agent를 읽기 전용으로 병렬 실행한다. 실제 코드 수정은 결과가 모인 뒤 별도 구현 Agent나 Main Agent가 담당한다.

Main Agent ├─ Git Agent: 최근 변경 조사 ├─ Profiler Agent: hot path 분석 └─ Test Agent: 느려진 시나리오 비교 ↓ 원인 후보 통합 → 우선순위 결정 → 한 Agent가 수정/검증

사용여러 Agent가 같은 파일을 동시에 고치게 하기보다 조사와 가설 검증부터 병렬화한다.

이 패턴이 맞는 이유: 각 조사 작업은 독립적이고, 최종 수정만 공유 상태를 필요로 하기 때문이다.

에이전트·툴 구성 펼치기

Manager가 작업을 나누고, Subagent가 독립적으로 처리하고, Manager가 결과를 합친다.

Manager ├─ Subagent A: 독립 작업 A ├─ Subagent B: 독립 작업 B └─ Subagent C: 독립 작업 C ↓ 병렬 실행 결과 반환 → 비교/통합 → 다음 작업
분할 기준
서로 기다리지 않아도 되는 작업, 별도 context가 유리한 작업을 나눈다.
격리
각 Agent가 별도 context나 workspace를 사용하면 중복 정보와 충돌을 줄일 수 있다.
통합 형식
각 Agent가 같은 형식으로 근거·결론·남은 문제를 반환하게 하면 Manager가 합치기 쉽다.
06

Skills

Agent가 반복해서 알아야 하는 업무 지식과 절차를 재사용 가능한 형태로 묶는 방식.

반복해서 설명하던 개발 지식과 절차를 묶어 두고, 필요한 작업에서 Agent가 읽어 사용하게 한다.작업 시작 → 필요한 Skill 로드 → 팀의 절차/지식 적용 → Tool 실행

적용 기준
같은 설명을 여러 작업에서 반복하고 있거나, 코드만 읽어서는 알기 어려운 사내 규칙이 있는 경우.
사용 방식
모든 지식을 하나의 거대한 프롬프트에 넣지 않는다. 업무별로 작게 분리하고 해당 작업에서 필요할 때만 로딩한다. 반복 실패가 발생한 지점이나 사람이 자주 설명하는 내용을 우선 Skill로 만든다.
장점
  • 도메인 지식 재사용: 모델이 매번 코드 전체를 역추론하지 않아도 팀의 규칙을 바로 사용할 수 있다.
  • 일관성: 빌드·테스트·보고 방식이 사람마다 달라지는 문제를 줄일 수 있다.
  • Context 절약: 필요한 Skill만 선택적으로 읽으면 항상 긴 시스템 프롬프트를 넣는 것보다 효율적이다.
단점
  • 노후화: 빌드 방식이 바뀌었는데 Skill이 옛날 내용이면 Agent가 잘못된 절차를 반복한다.
  • 과도한 지침: 세부 규칙을 너무 많이 넣으면 모델의 탐색 여지를 줄이고 context를 낭비한다.
  • 유지보수: 코드와 동일하게 변경·평가·버전 관리가 필요하다.

참고: Agent Skills · Microsoft — Skills

활용 예시 펼치기

Skill은 별도 Agent가 아니라 Agent가 반복해서 참고하는 업무 지식과 처리 절차 묶음이다. 같은 설명을 여러 번 하고 있다면 Skill 후보가 된다.

예시 1. 회사 출장 처리

상황출장을 준비할 때마다 회사 규정, 결재 기준, 예약 가능한 등급, 정산 방법을 Agent에게 다시 설명해야 한다.

구성“출장 처리 Skill”에 회사 정책, 필요한 서류, 승인 기준, 예약 시 주의사항, 정산 순서를 정리한다. 실제 예약·일정 확인은 Calendar/예약 Tool이 담당한다.

출장 요청 → 출장 Skill 로드 → 회사 규정에 맞는 조건 확인 → 필요한 정보/서류 확인 → 예약 Tool·Calendar Tool 실행 → 정산에 필요한 항목 안내

사용사용자는 “다음 주 일본 출장 준비해”처럼 업무만 요청한다. Agent는 필요한 Skill을 읽고 회사 규칙에 맞춰 같은 방식으로 처리한다.

이 패턴이 맞는 이유: 문제는 판단 능력보다 “우리 회사에서는 어떻게 하는가”라는 반복 지식이 부족한 것이기 때문이다.

예시 2. 사내 프로젝트 빌드·검증 절차

상황프로젝트마다 빌드 명령, 테스트 위치, 회귀 테스트 방식, 로그 경로가 달라 Agent가 자주 잘못된 명령을 사용한다.

구성프로젝트 Skill에 모듈 구조, 빌드법, 테스트법, benchmark 실행법, 자주 발생하는 오류를 짧게 정리한다.

버그 수정 요청 → 프로젝트 Skill 로드 → 올바른 빌드/테스트 경로 확인 → 코드 수정 → Skill에 정의된 검증 순서 수행 → 결과 보고

사용매 요청에 긴 개발 가이드를 붙이지 않고, 해당 프로젝트 작업일 때만 Skill을 불러오게 한다.

이 패턴이 맞는 이유: 매번 변하는 문제가 아니라 반복해서 필요한 팀 고유의 지식을 재사용하는 문제이기 때문이다.

에이전트·툴 구성 펼치기

Skill은 업무 설명서이고 Tool은 실행 수단이다. 둘을 분리해서 생각하면 쉽다.

Agent ├─ Skill: 회사/업무의 방법과 규칙 │ └─ "어떻게 해야 하는가" └─ Tool: 실제 조회/실행 기능 └─ "무엇을 할 수 있는가"
Skill 내용
반복 절차, 사내 규칙, 자주 틀리는 지점, 결과 형식 등 코드만 봐서는 알기 어려운 정보
분리 기준
업무별로 작게 나눠 필요한 순간에만 불러오게 한다.
관리
실제 프로세스가 바뀌면 Skill도 함께 수정하고, 과거 작업으로 동작을 다시 확인한다.
07

Tools / MCP

Tool은 Agent가 실제 행동하는 기능이고, MCP는 이런 Tool과 데이터를 연결하는 표준 방식이다.

Agent가 실제 시스템을 조회하거나 실행할 수 있게 기능을 연결한다. MCP는 이런 Tool과 데이터를 연결하는 표준 방식 중 하나다.Agent 판단 → Tool 호출 → 실제 시스템 결과 → 다음 판단

적용 기준
Agent가 대답만 하는 것이 아니라 실제 코드와 시스템을 확인하고 작업을 끝내야 하는 거의 모든 개발 자동화.
사용 방식
사람이 복사해서 주던 정보를 Tool로 직접 접근하게 한다. Tool은 기능을 작고 명확하게 만들고 성공/실패/결과를 구조화해서 반환한다. 여러 Agent 제품에서 같은 사내 시스템을 재사용해야 하면 MCP 서버로 제공하는 것이 유용하다.
장점
  • 실제 작업 가능: 코드 검색부터 수정, Build/Test, Issue 업데이트까지 한 실행 안에서 끝낼 수 있다.
  • 근거 기반 판단: 추측 대신 실제 로그, 테스트 결과, Git history를 보고 판단한다.
  • 연결 재사용: MCP를 사용하면 동일한 Tool을 여러 Agent/클라이언트에 연결하기 쉬워진다.
단점
  • Tool 품질 의존: 이름이 애매하거나 결과가 너무 길고 불명확하면 모델이 잘못 사용한다.
  • 도구 선택 비용: 수십·수백 개 Tool을 한 번에 노출하면 어떤 것을 써야 할지 판단 비용이 커진다.
  • 상태 변경 문제: 재시도로 같은 작업이 두 번 실행되지 않도록 idempotency와 rollback을 고려해야 한다.

참고: OpenAI — Harness engineering · MCP Specification

활용 예시 펼치기

Tool은 Agent가 실제 시스템을 보고 행동하게 만드는 기능이다. MCP는 이런 기능을 여러 Agent나 클라이언트에서 같은 방식으로 연결하기 위한 표준 인터페이스로 볼 수 있다.

예시 1. 영업 후속 업무 자동화

상황Agent가 “이번 주 후속 연락이 필요한 고객을 찾아 처리해”라는 요청을 받아도 CRM, 메일, 일정에 접근하지 못하면 목록만 추측할 수 있다.

구성CRM 조회 Tool, 이메일 Tool, Calendar Tool을 연결한다. Agent는 CRM에서 최근 연락과 계약 상태를 확인하고 필요한 후속 메일을 보내거나 미팅을 잡는다.

CRM 조회 → 후속 대상 선정 → 과거 메일/계약 상태 확인 → 고객별 다음 행동 판단 → 이메일 전송 또는 미팅 일정 생성 → CRM에 결과 기록

사용사람이 CRM 내용을 복사해서 Agent에게 주고, 답변을 다시 메일에 붙이는 과정을 없앤다. Agent가 필요한 데이터를 직접 보고 실제 행동까지 수행한다.

이 패턴이 맞는 이유: Agent 성능의 문제가 아니라 외부 시스템을 볼 수 없고 실행할 수 없는 것이 병목이기 때문이다.

예시 2. 이슈부터 수정·검증까지 한 번에 처리

상황개발 Agent가 이슈 내용은 알지만 CI 로그, Git history, 테스트 서버를 직접 보지 못하면 중간마다 사람이 정보를 전달해야 한다.

구성Issue 조회, Repository/Git, CI 로그, Build/Test, Regression 서버를 Tool로 연결한다. 여러 Agent 제품에서 같은 사내 시스템을 쓸 필요가 있으면 공통 MCP 서버로 제공할 수 있다.

Issue 조회 → 관련 CI 실패 확인 → Git 변경 조사 → 코드 수정 → Build/Test 실행 → Regression 서버에서 검증 → Issue에 결과 기록

사용사용자는 업무 목표만 전달하고, 필요한 증거 수집과 실행은 Agent가 Tool을 통해 직접 한다.

이 패턴이 맞는 이유: 자율 작업의 핵심은 모델에게 더 긴 지시를 주는 것보다 필요한 관찰·실행 수단을 직접 제공하는 데 있기 때문이다.

에이전트·툴 구성 펼치기

Agent가 실제 일을 끝내려면 필요한 정보를 볼 Tool과 행동할 Tool이 있어야 한다.

Agent ├─ 조회 Tool: CRM / Git / DB / 로그 / 문서 ├─ 실행 Tool: 메일 / 명령 / 수정 / 테스트 └─ MCP Server (선택) └─ 여러 Agent가 공통 Tool을 같은 방식으로 사용
Tool 설계
기능 이름과 입력을 명확하게 하고 결과는 짧고 구조적으로 반환한다.
Tool 범위
수십 개를 한꺼번에 붙이기보다 실제 업무 흐름에 필요한 관찰·실행 기능부터 연결한다.
MCP
같은 사내 시스템을 Codex, 다른 Agent, IDE 등 여러 클라이언트에서 재사용할 때 유용하다.
08

A2A

하나의 Agent가 Tool을 부르는 것이 아니라, 독립된 Agent에게 작업 자체를 위임하는 연결 방식.

하나의 Agent가 Tool을 호출하는 것이 아니라, 독립적으로 운영되는 다른 Agent에게 작업 자체를 맡긴다.Agent A → 작업 요청 → Agent B가 자체 Tool로 처리 → 상태/결과 반환

적용 기준
개발, 검증, 릴리스처럼 Agent 시스템이 실제로 서로 다른 팀·서비스·보안 경계에서 독립 운영되는 경우.
사용 방식
각 Agent가 담당 capability를 공개하고 task 단위로 요청한다. 상대 Agent는 내부 Tool과 Workflow를 사용해 작업하고 상태/결과를 돌려준다. 같은 프로세스 안의 단순 기능 호출이라면 A2A보다 Tool API가 보통 더 단순하다.
장점
  • 독립성: 각 팀이 Agent 내부 구현과 모델을 독립적으로 바꿀 수 있다.
  • 기존 Agent 재사용: 이미 운영 중인 전문 Agent를 다른 Agent가 하나의 capability처럼 이용할 수 있다.
  • 조직 경계 대응: 한 Agent에 모든 권한과 시스템 접근을 몰아넣지 않고 서비스 경계를 유지할 수 있다.
단점
  • 분산 시스템 복잡도: timeout, 부분 실패, 재시도, 버전 호환, 상태 추적이 필요하다.
  • 과한 설계 가능성: 하나의 Agent 내부 Tool 호출이면 끝날 일을 A2A로 만들면 운영 요소만 늘어난다.
  • 결과 통합: 여러 Agent의 상태와 책임 범위를 추적할 관찰성이 필요하다.

참고: A2A Specification

활용 예시 펼치기

A2A는 한 Agent 내부의 기능 분리가 아니라 서로 독립적으로 운영되는 Agent 시스템끼리 업무를 주고받는 경우에 쓴다. 같은 프로그램 안에서 끝나는 작업이라면 Tool이나 Subagent가 더 단순하다.

예시 1. 영업 Agent와 법무 Agent 협업

상황영업팀은 CRM과 고객 정보를 다루는 Agent를 운영하고, 법무팀은 계약서와 사내 법무 규정을 다루는 별도 Agent를 운영한다. 두 시스템은 관리 팀과 데이터가 다르다.

구성영업 Agent가 “이 계약의 위험 항목을 검토해 달라”는 task를 법무 Agent에 전달한다. 법무 Agent는 자기 문서와 Tool을 사용해 검토한 뒤 구조화된 결과를 돌려준다.

영업 Agent: 계약 협상 진행 → 법무 Agent에 계약 검토 task 전달 → 법무 Agent: 조항 분석 + 사내 기준 확인 → 위험 조항/수정안 반환 → 영업 Agent가 고객 대응에 반영

사용영업 Agent가 법무 데이터에 직접 접근하거나 법무 로직을 복제하지 않는다. 전문 영역은 해당 Agent가 책임진다.

이 패턴이 맞는 이유: 서로 다른 조직과 시스템 경계를 유지하면서 전문 Agent를 재사용해야 하기 때문이다.

예시 2. 개발 Agent → QA Agent → Release Agent

상황개발, 검증, 릴리스가 각각 독립된 자동화 시스템으로 운영되고 각 시스템이 자체 환경과 Tool을 가진다.

구성개발 Agent가 수정 결과와 검증 요청을 QA Agent에 task로 전달한다. QA Agent가 별도 Test Farm에서 회귀 검증하고 통과 결과를 Release Agent에 전달한다.

개발 Agent: 코드 수정/단위 테스트 → QA Agent: 독립 환경 회귀 테스트 → 실패: 원인/재현 정보 반환 → 개발 Agent 재수정 → 통과: Release Agent에 결과 전달 → Release Agent: 릴리스 조건 확인 및 진행

사용각 Agent는 상대 Agent 내부가 어떻게 구현됐는지 알 필요 없이 task와 결과 규약만 맞춘다.

이 패턴이 맞는 이유: 하나의 Agent가 모든 시스템을 직접 다루는 것보다 이미 독립 운영 중인 Agent끼리 업무를 연결하는 편이 자연스러운 규모이기 때문이다.

에이전트·툴 구성 펼치기

각 Agent가 이미 독립 서비스와 자체 Tool을 가지고 있을 때, task와 결과를 주고받는 계층을 추가한다.

Agent A ── task ──▶ Agent B │ │ 자체 데이터/Tool 자체 데이터/Tool │ │ └──── status/result ◀┘
Task 규약
무엇을 요청하고 어떤 상태와 결과를 반환하는지 공통 형식이 필요하다.
독립 실행
상대 Agent는 내부 Tool과 Workflow를 스스로 선택해 task를 처리한다.
사용 기준
같은 애플리케이션 안의 기능 분리라면 Subagent/Tool이 더 단순하고, 팀·서비스 경계가 있을 때 A2A를 고려한다.

패턴은 보통 조합해서 사용한다. 아래는 개발 업무를 시작할 때의 기본 조합이다.

4. 활용 시 고려사항

아래는 패턴 자체가 아니라 Agent를 실제 운영할 때 성능과 정확도에 영향을 주는 조건이다.

자동 검증

사람 승인을 반복 단계의 기본값으로 두면 처리량이 급격히 떨어진다. Build, unit test, regression, benchmark, static analysis, runtime check처럼 Agent가 스스로 확인할 수 있는 독립 신호를 늘리는 쪽이 중요하다.

환경 관찰성

사람이 로그·스크린샷·실행 결과를 복사해 주는 구조를 줄인다. Agent가 로그, metrics, traces, UI, profiler 결과를 직접 읽을 수 있어야 긴 작업을 독립적으로 끝낼 수 있다.

실행과 복구

자율성을 낮추는 것보다 격리된 branch/worktree, 재현 가능한 환경, checkpoint, rollback을 제공해 실패해도 쉽게 복구되도록 만든다. 권한 문제는 작업 위험도와 실행 환경에 맞춰 별도로 설계한다.

Context 관리

모든 문서·로그·Tool을 한 번에 넣지 않는다. Skill의 선택적 로딩, 검색, 요약, subagent context 분리, repository-local 문서를 이용해 필요한 정보만 공급한다.

Tool 품질

Tool 이름과 반환값이 명확해야 한다. 긴 텍스트를 그대로 반환하기보다 검색·필터·구조화된 결과를 제공한다. 상태 변경 Tool은 retry와 idempotency가 필요하다.

평가 세트

Agent 개선은 체감만으로 판단하기 어렵다. 과거 버그·실패 CI·성능 문제를 평가 세트로 만들어 성공률, 소요 시간, Tool 호출 수, 비용을 비교한다.

Multi-Agent 비용

역할 이름을 나누기 위해 Subagent를 쓰지 않는다. 병렬화 가능한 작업, context 분리가 필요한 작업, 여러 가설 동시 검증처럼 명확한 이득이 있을 때만 사용한다.

사람의 역할

반복 실행·검증·리뷰를 사람이 담당하지 않도록 시스템화하고, 사람은 목표 설정·새 기준 정의·예외적인 고위험 판단에 집중하는 편이 전체 처리량에 유리하다.

5. 선택 기준

진행 순서가 고정되어 있는가? ├─ Yes → Workflow + Agent └─ No → Agent Loop + Tool 작업이 길고 상태 관리가 필요한가? └─ Yes → Planner 추가 결과를 자동 검토해야 하는가? └─ Yes → Evaluator 추가 독립 작업을 실제로 병렬 실행할 수 있는가? └─ Yes → Subagents 추가 반복되는 사내 지식·절차가 있는가? └─ Yes → Skills 추가 외부 시스템을 직접 사용해야 하는가? └─ Yes → Tools / MCP 독립 Agent 서비스 간 협업인가? └─ Yes → A2A
